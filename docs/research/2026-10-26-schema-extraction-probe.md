# 住宿制度结构约束抽取试验

本试验借鉴 OneKE 的“指定事件及字段约束后抽取”思路，未安装或运行 OneKE，不能作为 OneKE 框架效果评测。参考项目及事件约束示例：

- https://github.com/zjunlp/OneKE
- https://github.com/zjunlp/OneKE/blob/main/examples/config/EE.yaml

## 输入和控制

复用先前 V2 的四条样本：住宿办法第六条第一项（分配调整职责）、第九条、第十条、第十一条。各条输入包括目标原文和直接父条款，不加入手写标准答案。两个模型使用同一份提示词、相同字段结构及来源校验，无自动重抽。

模型为现有本地 `qwen2.5:7b-instruct` 和已配置的 `deepseek-flash`。温度为零，单次最大输出 3500 tokens。后者禁用思考模式；模型接口不同，不能把该对照解释为仅模型规模的单变量因果实验。

字段包括动作主体、动作、对象、接收方、原则性措辞、条件、前提、时间和例外，每个非空字段独立提供连续原文及条款 ID。未知主体允许为空，不强行填充。输出不写入业务数据库，也不建图或接入正式 MCP。

## 实际结果

| 样本 | Qwen 通过来源校验 / 无效 | DeepSeek 通过来源校验 / 无效 |
| --- | --- | --- |
| 第六条第一项 | 0 / 0（返回空规则） | 2 / 0 |
| 第九条 | 3 / 2 | 5 / 0 |
| 第十条 | 1 / 1 | 7 / 0 |
| 第十一条 | 1 / 4 | 7 / 0 |
| 合计 | 5 / 7 | 21 / 0 |

以上是候选数量，不是召回率或准确率。拆分粒度不同，不能直接用规则条数衡量好坏。旧 V2 与本试验结构及校验要求不同，不能比较“通过率”。

## 人工观察

DeepSeek 的第十条保留了禁止随意调换/出借和强占/出租、特殊情况按流程申请、审批通过后的后勤执行及房源约束、原则办理月份、特殊原因随时申请及经审批后的调整。没有生成原文未明确的审批部门；申请接收方也保持未知。相比旧 V2 将“需调换”当成义务动作，这次将“按规定流程申请”识别为义务动作。

同结构下的 Qwen 仍出现申请主体缺失、把后勤执行部门当成申请接收方，以及将办理月份与特殊申请混在一个动作记录中的问题。部分语义问题能通过来源校验，因为对应词语确实出现在原文中。

DeepSeek 也不能直接视为生产规则：

1. 当前 schema 只提供分条记录，没有组装“同一办理情形”，也没有明确的 exception_to 或规则间依赖关系；一般办理时间与特殊申请的覆盖关系仍需理解原文。
2. 部分执行动作的记录没有重复携带其前文的适用条件。单独消费一条规则可能扩大适用范围。
3. role 分类不是业务语义正确性的保证，例如服从管理被归类为 execution，只能作为候选。
4. 未使用独立人工标注集，未评估全库覆盖和稳定性。

## 结论和边界

当前本地抽取不佳，不能据此归因为制度无法结构化。明确字段和逐字段依据配合不同模型，可以得到显著更完整的小样本候选。

但“抽取可以改善”和“图谱能改善当前 MCP 问答”是两个命题。本次只验证前者，没有修改正式 MCP，也没有完成实际 Agent 调用链的端到端效果比较。若继续验证收益，应固定检索原文、生成模型和问题，再比较是否加入规则候选；不能把换用生成模型、补充原文和图谱本身的收益混为一谈。
